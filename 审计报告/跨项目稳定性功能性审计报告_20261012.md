### 关键根因分析：`atomic_json.py` 与 fixed_tmp_replace_nonatomic

`butler/core/atomic_json.py` 是 doubao-butler 的**整份 JSON 原子写工具**，被 5 处生产代码复用（`config_routes.py:49`、`deps.py:59`、`doubao_webhook.py:303`、`core/aliases.py:48`、`atomic_json.py:29` 自身）。

规则 `py.fixed_tmp_replace_nonatomic` 报其为缺陷：固定名 tmp（`x.json.tmp`）+ `os.replace`，并发写者交错后最后一次 replace 装上坏数据。

**但这是有意设计**——`atomic_json.py` docstring 明写：

> 临时文件用**固定名**（⛔ 随机后缀/uuid）：崩窗留下的固定名会被下一轮整文件覆盖，随机后缀则每崩一次多一个孤儿，违反开发规范的 ⛔ .bak 堆积。

**真实风险点不在 atomic_json 本身，而在调用方是否正确处理 `read_json_object` 返回的 `unreadable` 标志**：
- `read_json_object(path)` 返回 `(data, unreadable)`，区分"读不出"和"本来没有"
- 若调用方忽略 `unreadable=True`，把残缺数据当完整数据做整份覆盖写入 → **抹掉历史**（doubao-butler 第一轮审计 D1/D2/D4 缺陷）

**triage 结论**：`py.fixed_tmp_replace_nonatomic` 在 atomic_json.py 上为**假阳性（有意设计）**；但需核 5 个调用方是否检查 `unreadable`。规则本身应增加"被调方语义"判据（PITFALLS P6 通则）。

### 假阳性确证：py.rmw_silent_empty

`llm.py:210` 和 `newapi.py:177/182` 被报"读失败赋空容器且无留痕，随后写回将抹掉历史"。经核代码：

```python
# llm.py:210 — 解析工具调用参数
try:
    args = json.loads(tc["function"]["arguments"] or "{}")
except Exception:
    args = {}  # ← 临时变量，不写回历史，非 rmw

# newapi.py:177 — 解析 DB 字段
try:
    models_list = json.loads(ch["models"] or "[]")
except (JSONDecodeError, TypeError):
    models_list = []  # ← 同上，局部默认值
```

这些是**局部变量解析失败赋默认值**，不是"读持久状态失败后写回覆盖"。**假阳性**。规则应排除"赋值目标是局部变量且不回写"的形态。

## 十一、跨项目共性缺陷

### 共性 A：网络/IO 调用无 timeout（跨 7 项目）

| 项目 | 位置 | 调用 |
|---|---|---|
| deepseek-pp | webdav-client.ts, oauth-client.ts | 裸 fetch 无 AbortSignal |
| deepseek-studio | spawn_child stdout 管道 | 无读取超时 |
| xiaotiancai | DecisionActivity.kt x2, CourseFragment.kt | HttpURLConnection 无 timeout（且未 disconnect） |
| PosterWall | user.js:4244 fetchDetailPageImages | GM_xmlhttpRequest 无 timeout |
| TVPilot | mqtt_worker _action_q.get() | 阻塞无 timeout |
| DeskPilot | xfyun_msc.py QTTSAudioGet/IAT while True、pm_forward communicate、http.request、ws.py collect_status 同步采集 | SDK 循环 + subprocess + Node http + 定时广播采集全无超时 |
| memory-agent | ma.llm_call_no_timeout 规则 | 外部模型/向量端点无超时（规则 testing 状态） |
| AutoForge | af.mcp_tool_no_timeout 规则 | MCP 工具调用无超时（F1 族） |

**通则**：网络/IO 调用必须设 timeout，且 timeout 必须在**底层**（fetch/urlopen/HttpURLConnection/SDK 循环层），不能只在调用方的 barrier 层。两个反例：
- deepseek-pp 的 recovery barrier 有 10s 超时但底层 fetch 无 AbortSignal——barrier 超时后 fetch 仍挂起，治标不治本。
- DeskPilot electron/main.js:630 设了 `timeout:30000` 选项但**未绑 'timeout' 事件监听器**，Node 的 timeout 选项不自动中止请求，等于没设。

### 共性 B：资源未释放（跨 5 项目）

| 项目 | 资源 | 后果 |
|---|---|---|
| xiaotiancai | HttpURLConnection 未 disconnect | socket 泄漏→耗尽 FD |
| PosterWall | sqlite3 连接未 close | await 期间持锁→database is locked |
| deepseek-studio | sidecar 子进程未 Job Object 级联杀 | 孤儿进程占用端口 |
| DeskPilot | service.py/supervisor.py open() 不用 with 传 Popen | 每次 gateway 重启泄漏 2 句柄→耗尽 FD |
| deepseek-pp | MV3 SW 终止时 activeRunLeases 丢失 | 靠持久化存储恢复（已正确处理） |

### 共性 C：错误路径状态不复位（跨 3 项目）

| 项目 | 位置 | 缺陷 |
|---|---|---|
| deepseek-pp | active-client.ts:282-296 | storage 持续失败时"永远刷新永远失败"循环无错误表面化 |
| deepseek-studio | main.ts:84-88 | loadConfig 静默吞错，回退默认覆盖原配置 |
| PosterWall | main.py:88-107 | download 冷却在 qB 失败路径不复位 |

### 共性 D：读失败静默降级 → 写侧覆盖（AutoForge + doubao-butler）

这是 auditkit 规则覆盖最深的缺陷族：
- AutoForge F8/F9/F10/F11/F13：读侧宽捕 Exception 后静默返回空值，写侧全量覆盖
- doubao-butler atomic_json 调用方：若忽略 `unreadable=True`，残缺数据当完整数据覆盖

**根因**：读路径的失败被当成"没有数据"。修复通则——读失败必须留痕，且写侧在 `unreadable=True` 时**拒绝整份覆盖**。

### 共性 E：死代码/失效功能（TVPilot）

TVPilot 的 alerts.py / hdmi3_monitor.py / stats.py 三个模块从未被导入，patch 脚本锚点失效。开发者以为告警/HDMI3/stats 功能在工作，实际从未加载。**这是"假绿"的最危险形态——功能看起来在工作但实际不存在。**

### 共性 F：except 返回放行值 fail-open（memory-agent 重灾区）

memory-agent 主源码有 4 处 `except: return True`（identity/activity_inference/intent_inference/template_validate），语义为"放行/命中/通过"。异常时放行 = fail-open，安全/一致性风险。doubao-butler 的 conflict.py:147 同类。

### 共性 G：无界模块级 dict/set（跨 6 项目）

| 项目 | 位置 | 容器 |
|---|---|---|
| DeskPilot | agent.py _sessions/_session_timestamps、agent_loop.py _processed_*、butler.py _butler_sessions、chat.ts messages | session 缓存/去重 set/消息数组只增不减 |
| AutoForge | af_runtime._exec_stats、af_proposal.order 等 | 进程级单例无界增长 |
| memory-agent | entity_resolution.priors、identity._needs_review、template_validate.fixes、vision_service._skip_counts | 累加容器无淘汰 |
| TVPilot | logos._logo_cache | 无淘汰策略 |
| doubao-butler | （规则命中 152 处，含噪音） | unbounded_container |
| PosterWall | （前端缓存） | — |

**通则**：长期运行的服务进程，所有"只进不出"的模块级容器（session 表、去重 set、缓存、历史）必须有 LRU/TTL/容量上限淘汰策略，否则内存随进程寿命单调上涨。

### 共性 H：C SDK while 循环无总超时（DeskPilot 特有）

DeskPilot 的讯飞 SDK 调用（QTTSAudioGet 合成、QISRGetResult 识别、feed_audio）全是 `while True` 循环，仅靠 SDK 返回的状态码退出，无总超时/最大迭代守卫。SDK 状态机卡死时线程永久占用。**应在循环外加总超时守卫，而非依赖 SDK 自身正确性。**
