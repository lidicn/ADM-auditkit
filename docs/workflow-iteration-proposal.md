# 工作流迭代提案：把「实测」提升为一等公民

> 来源：对 `lidicn/AutoForge` 连续二十轮审计（1237 条机器命中 → 收敛为 16 项确证缺陷）过程中积累的经验。
> 提交者：元宝 · 2026-10-07
> 目标：这些是可被上游 `ADM-auditkit` 吸收的**机制级**改进，不是针对某个项目的规则补丁。

---

## 0. 一句话背景

我们在这二十轮里最深刻的教训不是"找到了什么缺陷"，而是：

**静态命中不可信，实测才可信；而实测工具自己也会失效，且失效时表现为"结论变好"而非报错。**

后者的危害远大于前者——它让人以为缺陷被修好了。

---

## 1. 建议一：把 PoC 做成流水线的一等阶段（最高优先级）

### 现状

指南描述的流程以"规则 → 命中 → 报告"为主轴。我们二十轮里真正让结论变可信的，是把每一族静态命中都落到**行为级实测**。

### 建议形态

四类 PoC 覆盖四个缺陷族，每类协议固定：

| 类别 | 静态规则族 | 协议 |
|---|---|---|
| **递归** | 无预算 / 无环检测 | 构造自引用 + 深度阶梯（50/200/1000/3000），子进程隔离跑 |
| **状态损坏** | 破坏性覆盖 | 播种 → 快照 → 损坏 → 复测 → 比对盘上字节 |
| **出站** | 护栏旁路 | 起本地 HTTP 服务做重定向靶子，看是否取回白名单外内容 |
| **失败开放** | fail-open 守卫 | 播种 → 基线（应拦住）→ 损坏 → 复测（放行？）→ 端到端（覆盖真的发生？） |

### 为什么值得上游内置

- **递归 PoC** 让 F6 从"第二轮提出"到"第十九轮才确证"——中间十七轮它一直是静态命中 + 人工推理，因为探针构造不出 `Trigger` 对象。若上游内置，第一天就能确证。
- **失败开放 PoC** 让 F12 的严重度被重新认识：第五轮人工只验到"守卫放行"，第十八轮自动 PoC 走完链路，证实**放行的后果是另一条归档被真覆盖**。这是静态分析永远给不出的信息。

### 关键：协议里必须包含「后果」

失败开放 PoC 最容易写错的一步是只验"守卫放不放行"。必须追问**放行之后操作是否真的发生了**（`save()` 返回成功？文件被覆盖了？）。我们第一版就少这一步。

## 2. 建议二：证据强度分级（强烈建议）

不同实测手段的证据强度**差一个数量级**，混在一起报会虚增确证强度。我们最终用了四档：

| 档位 | 含义 | 触发条件 |
|---|---|---|
| `confirmed` | 真实输入实测崩/丢 | 输入的每个字段都是真实类型 |
| `via_fallback` | 降级替身触发 | 真实形状构造不出，用"能自展开的替身"让递归至少跑起来 |
| `via_stub` | 依赖桩触发 | 模块因私有依赖导入不了，注入桩后才跑起来（`homesdk` 要求 Python≥3.11，环境 3.10） |
| `safe_manual` | 手工探针结论 | 自动探针在该目标上失控，改受控手工跑 |

**`unavailable`（测不到）与 `safe`（没问题）必须严格分开。** 这是最容易出错的地方：两者在报表里长得一模一样，都是"没有崩溃记录"。我们第十九轮修掉的一批假阴性，全部是 `unavailable` 被当成了 `safe`。

建议 Finding 结构里直接带 `evidence_strength` 字段，报告层按强度分层展示。

## 3. 建议三：探针必须对自身设资源上限

### 事故

我们有一个目标（`af_nl_parse._build`）让整个沙箱反复 HTTP 502（十九、二十两轮共 8 次）。而**手工单独跑它只要 1.5–2.4 秒**，10 次调用全部正常返回。

失控的是探针宿主进程，不是被测函数。

### 更严重的同类事故

第八轮，状态损坏探针把**审计工具链自己的源文件写坏了**，`core/` 下 300+ 文件受损——一个"测数据会不会丢"的探针，把宿主数据弄丢了。它用一次事故验证了被测缺陷的破坏力。

### 建议

PoC 框架层统一施加：

```python
resource.setrlimit(resource.RLIMIT_AS,  (2_000_000_000, 2_000_000_000))
resource.setrlimit(resource.RLIMIT_CPU, (60, 60))
```

并且——**我们加了之后仍在 `_build` 上复现，根因未定位**。所以更重要的建议是：

- PoC 必须**逐目标 flush 进度日志**，否则卡死时看不出卡在哪一个上
- PoC 结果应**逐目标增量落盘**，挂了也不丢已完成部分
- 写盘类探针必须强制使用临时目录 + 白名单，不允许触碰工作区

## 4. 建议四：判据增补（YAML 规则层面）

已在规则提案 `20261007_185543_l3_rules` 里附了可复现样本，这里重述结论：

### 4.1 `call` 判据穿透 BoolOp / IfExp

```python
self._opener = opener or urllib.request.urlopen              # 漏检
with (opener or urllib.request.urlopen)(req, ...) as resp:   # 漏检
```

取 `func` 末段名时向下穿透 `BoolOp` / `IfExp` / `Starred` / 下标。**能立刻覆盖的一处**（`af_registry.py:321`），成本低。

### 4.2 `regex` 仅扫代码、跳过注释与字符串

实测 clean 样本 `MSG = "不要使用 except Exception: 这种写法"` 被误命中——正则扫到字符串字面量。建议加 `regex_src_only: true` 或默认剥离注释与字符串。

### 4.3 需要跨语句 join 的判据（二十轮最有价值的两族，YAML 5 判据无法表达）

这两族合起来贡献了我们 16 项确证缺陷中的 7 项，**是投入产出比最高的判据**，但现有 5 种判据（call/attr/name/type/regex）表达不了：

**DO —— 破坏性覆盖**（读侧静默返空 + 写侧全量覆盖）。四种子形态：

- DO-01 读侧 `return {}` / 空骨架
- DO-02 读侧 **void 静默 return**（数据经实例字段流转，函数本身没返回空值）
- DO-03 **读和写在同一个函数体内**
- DO-04 **读侧在别的模块**（跨模块 join 天然失效，我们第六轮才补上）

**FO —— 失败开放守卫**（读失败 ⇒ 守卫放行）。它的识别难点：

> `af_store._dir_owner` 既不叫 `assert_*` 也不 `raise`，**守卫性质完全来自调用方那句 `owner is not None`**。只看函数自身根本看不出它是守卫。

建议引入"函数返回空值 + 该返回值被用于守卫判断"的跨语句模式，而不是依赖命名约定。

## 5. 建议五：分诊层加「缓释标记答非所问」信号

### 背景

源码里常有 `审计 BUG-01…BUG-20` 这类修复注释。直觉是把注释当"已修证据"**减分**。我们第十三轮踩了个反直觉的坑：

`af_auth.py` 有注释（BUG-20）："`_persist` 是全量覆盖写，不重读就会把别的进程刚写入的码整片抹掉"。

分诊把它判成"已修标记"减 80 分，于是 F10 三处凭证存储**从未进过 Top 16**。

但注释说的是"防住了**不重读**"，缺陷是"没防住**重读失败**"——**注释恰恰是最有力的证据，却被当成了缓释证据**。

### 建议

每条规则声明自己关心什么词（`concerns: [...]`）。注释里有"已修/已修复"标记却**不含**本规则关心的词 ⇒ **加分而非减分**（我们用的是 +40 vs −80，反转 120 分）。

改完效果：`af_auth:539/665` 从未进 Top 16 → 升到第 4、5 名。

## 7. 附：十一次「工具/环境静默失效」清单

这是我们最想传递的一条工程纪律的证据。十一次事故**无一例外**表现为"结论变好 / 命中变少"，而不是报错：

| # | 失效源 | 表现 |
|---|---|---|
| 1 | `scripts/` 漏扫（路径拼错） | `gone=125`，看着像修复进展，实际一条没修 |
| 2 | 写盘调用别名表缺 `_atomic_write_text` | 规则安静地 0 命中 |
| 3 | RES-03 用全文件正则冒充数据流 | 文件里任何一处字符串 join 就让所有线程判为"已 join" |
| 4 | 抑制锚点用行号 | 行号一漂 ⇒ 抑制静默失效 ⇒ 缺陷以 `new` 身份重现 |
| 5 | `glob` 跳过点目录 | `.catalog/` 下状态根本没进快照 |
| 6 | `_fetch_stub` 只返回一个实体 | 手工用例与自动探针用了不同输入，结论打架 |
| 7 | 补丁少导入 + 被宽 `except` 吞 | 修了等于没修，且 PoC 判不出 |
| 8 | bandit 认不出间接调用形态 | 漏 2 处，看着像"只有 2 处" |
| 9 | 外部工具跨 bash 调用丢失 | 0 命中，与"扫过没问题"无法区分 |
| 10 | `NestStandin.__iter__` 返回空迭代 | 循环体一次不执行 ⇒ 判"没问题" |
| 11 | 探针卡死宿主 | 整个轮次 HTTP 502 |

**失效源的位置一路外移**：我们写的分析器 → 补丁 → 外部工具 → 环境 → 探针自身。

### 由此提炼的两条建议

1. **任何"命中变少"或"结论变好"，必须先怀疑工具与环境，再相信结论。** 建议把这个写进指南的显眼位置。
2. **给分析器加"零命中即报警"的门限。** 我们第十六轮靠这条把"工具没了"暴露成 FAIL——但它当时的**报错方向是错的**（说"规则可能失效"，真实原因是"工具没了"），诊断方向错了修起来就白费劲。建议门禁同时输出 `status: tools_missing / ok / ok_but_no_hit` 三态，而不是笼统的"0 命中"。
