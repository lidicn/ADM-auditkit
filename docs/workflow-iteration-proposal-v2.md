## 二、核心诊断

### 2.1 成本结构三分法

| 成本块 | 性质 | 随什么增长 |
|---|---|---|
| 平台 + 规则库 | 固定成本，已沉没，三项目共享 | 一次性 |
| 扫描（round） | 分钟级，docker exec 一条命令 | 代码量（线性但系数极小） |
| **triage（人工裁决）** | **真正的大头** | **命中数 × 噪比，与代码量无关** |

结论：
- **不是"重型武器只有大项目配用"**——扫描边际成本趋近零，阈值在 triage 人时；
- 小而关键（AutoForge 91k，写物理设备）> 大而寻常；
- 工作流的经济学是**前置付费、后置免费**：首轮贵（写规则+校准假阳性），
  之后每轮便宜且可复用。显得低效的场景只有一个：对已人工审计过的目标
  重复付全景全款（本次 6 轮中至少 4 轮如此）。

### 2.2 分工本质：复印机 vs 发明器

- **工作流轮 = 模式复印机**：规则库是过往发现的**化石**，只能机械放大
  "已经有人想过的缺陷类"，原则上不可能发明新类。规则库越厚，
  纯工作流轮的边际产出越趋近零（低垂果实已被探索轮摘完）；
- **探索轮 = 模式发明器**：带假设读代码，理解意图，找"没人想过要找"的
  语义/时序/设计类缺陷。**缺陷经验的唯一来源是探索**；
- 工作流轮沉淀的是**平台经验**（matcher AND 语义、own_walk 不下钻、
  注解赋值漏判、Lambda 无 name——本次 6 轮的真收获），让工具更好，
  但不让审计更准。两类经验都值钱，不可互相替代。

### 2.3 三项目"一次扫完"的对错

- ✅ 扫描应该批量：一条 for 循环三个 round，分钟级；
- ❌ triage 不该批量：一次囤 3×500+ 条待裁决是反模式，注意力稀释后
  哪个项目都收敛不了；
- ✅ 真正值得批量的单位是**规则资产与裁决洞察**：fixed-tmp 一条规则在
  AutoForge 命中 6 处，同一洞察直接复扫另两项目，命中即高置信，
  不用重新校准；canary/flock 语义型假阳性在规则层修一次，三项目同愈。

**正确姿势：批量扫描、分批裁决（按 criticality 排队）、洞察回灌规则。**

## 三、缺失的一环：R0 轻装探索轮（本建议书最重要的一条）

### 3.1 问题

当前工作流从基线轮直接起步，规则库没有"进货渠道"——
没有探索轮持续供给新缺陷类，规则库相对于演化中的代码和威胁模型
只会单调衰减。本次会话验证：工作流的全部弹药（fixed-tmp、cross-func、
security-sync）的模式原型**全部来自之前的人工探索轮**。

### 3.2 推荐轮次模板

```
R0 轻装探索轮（假设驱动、按模块切片、不看机器命中行号）
     ↓【沉淀出口·规定动作】可机械化的发现 → 当场起草规则 + 回归护栏
R1 基线轮（全景 round，校准新规则，建立噪音地图）
     ↓ triage：探索 ∪ 轮次 去重合并
R2+ 回归轮（delta/regression 模式，三项目并扫，分钟级守夜）
```

### 3.3 三条落地细则

1. **探索必须在"看机器 findings 之前"**——防止自动化偏见（锚定在
   findings 清单上逐条核对，丧失自己提假设的能力）。基线可先跑，
   但只喂探索 agent 一张"噪音地图"（哪些规则是信号型、大族在哪、
   哪些模块已深审过），**不给具体命中行号**；
2. **沉淀出口必须是规定动作**——探索结束后强制回答
   "这批发现里哪些可机械化？"，当场写规则。不设此环节，
   探索经验散在报告里，下次换个 agent 全忘。本次会话是 agent
   自觉做了这一步，它应该是工作流的明文步骤；
3. **探索轮按 criticality 排期，不做三项目齐步走**——探索贵
   （agent 全神读代码），工作流便宜（分钟级）。建议每次只切一个
   模块/功能切片。AutoForge 已走过 R0；doubao-butler 263k 值得一轮
   切片式探索；memory-agent 先画像瘦身（4592 文件 1.4M 行明显混入
   非源码，否则扫描与 triage 都被杂音稀释）。

## 四、平台迭代建议（按优先级）

### P0：直接可修的平台缺陷

1. **`propose create` 改动文件收集失效**：git status 明明 7 个变更，
   `files_changed: []`，本次靠手动补齐才成包。疑似在错误目录跑 git
   或只认 staged。修好后提案自动化才闭环；
2. **共享判据变更无联动验证**：改 `legacy/analyzers/_common.py` 后
   只能整轮重跑 553 条验证 -4 假阳性。建议：规则依赖的共享模块变更时，
   自动对**上一轮该规则的命中集**做 hit-set diff（added/removed），
   分钟级验证召回/精确率变化，不用全量新轮次。

### P1：把"记忆"变成平台能力（本次最大的重复成本）

3. **triage 裁决落盘**：加 `auditkit triage accept/reject --reason`，
   按 (rule, file, pattern) 写进项目 profile；后续轮次自动标"已裁决"，
   只增量报新命中。canary:103、flock:132 这类"语义不成立"的假阳性
   本次裁了，下个 agent 还得重裁——**此条能把回归轮 triage 成本
   砍到接近零**；
4. **裁决区分"不采纳"与"已知未修"**：确证候选（如 C 类 6 条无界容器）
   进 bugs.json 台账（status AutoForge 目前没有），修复后复扫归零
   才算闭合。审计平台与缺陷台账打通，才能量化"确证率"；
5. **轮次模式分流**：`full`（首扫）/ `delta`（只审 git diff 涉及文件）/
   `targeted`（规则子集）/ `regression`（仅确证 bug 对应规则）。
   本次 6 轮至少 4 轮在重复付全景全款；delta 模式对活跃仓库能让
   边际成本降一个数量级；
6. **规则意图标签** `discovery` / `regression`：给已修复历史缺陷写的
   规则（cross_func、security_sync）标 regression——0 命中是**成功**
   而非可疑，豁免 N1 零命中排查预算，也不进 triage 队列。

### P2：降噪与校准摩擦

7. **高噪规则内置收窄变体**：PITFALLS 已有方法论（宽捕后是否接
   全量覆盖写），把它编成 silent_except 的规则变体而非文档建议——
   319 条能收到个位数高价值命中；
8. **无界容器规则加生命周期启发式**：按调用构建即弃的 `_Builder`
   （B 类）与进程级单例 `_history`（A 类）同 severity 报出，本次
   29 条里 8 条是这类。对象在函数体内创建且不落 self/module → 降级
   或不报；
9. **规则命中集入库做版本回归**：规则 bump 版本时自动 diff 新旧
   命中集，校准从"改-scp-整轮重跑-人眼比对"（本次跑了 3 遍）
   变成一条命令。

## 五、给项目方（使用侧）的用法建议

1. **全景扫只在首轮付一次**：三个项目均有审计史，别再付全款；
   切 delta + regression 模式，三项目每轮一起跑，分钟级；
2. **triage 排队按 criticality**：AutoForge（写物理设备）>
   memory-agent > doubao-butler；单次会话只裁一个项目的队列，
   裁完回灌规则再开下一个；
3. **memory-agent 先画像瘦身**再定审计深度；
4. **doubao-butler 做下一次全景校准场**：263k 行、3 倍噪声压力，
   比在 AutoForge 上继续磨更能验证通用规则的鲁棒性；
5. **每个项目按 R0 模板补一轮切片式探索**（见第三节）。

---

## 六、一句话总结

> 工作流不重，重的是裁决纪律；规则库不缺数量，缺进货渠道。
> 落两件事即可常态事半功倍：**R0 探索轮 + 裁决落盘**——
> 探索负责发明模式，工作流负责复印模式，台账负责记住裁决。
> 三者闭环后，审计从"每轮全景重扫"变成"增量守夜"。
