# 工作流提案：审计产出物本身需要被审计

> 提交给 ADM-auditkit 维护者
> 基于 memory-agent 第三期二十轮审计实证（2026-10-10）

---

## 一、一句话主题

**前两期我提的是"规则能不能跨项目复用"和"要不要做 PoC"。这一期要提的是另一件事：我们为被测代码设了 34 项门禁，却从不为审计自己的产出物设门禁——而它失效时的表现，和被测代码的缺陷完全一样。**

---

## 二、铁证：M23

memory-agent 第三期第十九轮，工作流轮，不审计，只补盲区。补的是 COV-08「补丁自洽性」。

**19 轮的补丁全部躺在只读副本里，从来没有系统性验证过补丁自身是否正确。**

第一次验证做了什么？只是把 `patch_lint` 的护栏 API 名单从 doubao-butler 那套补上 memory-agent 这套（`state_poison.mark/guard`、`outbound_guard.validate_*`）。检查文件数 **0 → 5**。

**它立刻报出了 M23（high）：**

```python
try:
    from .state_poison import mark
    mark(self.users_file, exc)      # 置位：告诉写侧"读不出来，别覆盖"
except Exception:
    pass                             # ← 护栏自身失败，无声无息
```

实测确证：把 `mark` 换成必抛异常的桩函数 → 播种 alice/bob/carol → 损坏 `users.json` → `register('dave')` **返回 True** → 盘上只剩 `['dave']`，原三个账号全丢，**且日志无任何输出**。

**即 M6（破坏性覆盖）在"已修复"的代码里静默复发。**

这不是运气差。补丁从未被检查过，所以它"看起来一直是好的"。

## 三、"工具静默失效"的失效源一路外移

这条主线我记了二十几轮。把失效源按时间排开，能看到一条清晰的迁移路径：

| 阶段 | 失效源 | 典型 |
|---|---|---|
| 早期 | **分析器** | W69 async 节点漏判、W95 src-layout |
| 中期 | **补丁** | D16 参数传了但守卫没插 |
| 中期 | **外部工具 / 环境** | bandit 跨调用丢失、tomllib 在 3.10 不存在 |
| 中期 | **探针** | W102 适配器按项目硬编码、`check_same_thread` 漏传 |
| **本期** | **降噪规则** | W109 把 M6 判成 low |
| **本期** | **核验脚本** | W130 连错两版，两版都把"有保护"判成"无保护" |
| **本期** | **工作流配置自身** | focus.json 不是合法 JSON、coverage.json 条目字段全丢 |

**前 20 次在"被测侧"，这次全在"审计侧"。**

而两侧的表现完全一致：**静默，方向是"看起来没问题"，从不报错。**

## 四、本期六条建议

### ① 补丁必须过 PoC 与 patch_lint，且名单要自适应

当前 `patch_lint` 的护栏 API/模块名单按项目写死。memory-agent 的补丁因此 19 轮从未被 lint，输出是"检查 0 个含护栏调用的文件"——**和它上一版"检查 0 个文件 · OK"是同款结构缺陷（W76c），这次是第二次发作**。

建议：名单改为自适应（从补丁模块反查护栏 API）；**且检查 0 个文件时必须显式告警，不能输出 OK**。

> 这一条如果只在 doubao-butler 上修好、不推广，M23 就还会再发生一次。

### ② 把"被消除的命中"纳入门禁（降噪是双向的）

本期 medium 从 707 降到 370，**但我一度没有意识到：每一次降噪同时是一次"这些不是缺陷"的判断。**

统计下来，消除的 447 条**一条都没核验过**。建台账逐条核验后抓到 1 条误杀：

`auth.py:190 _load_users` 被判"有日志 ⇒ 有意降级 ⇒ low"——**而它就是 M6 本身**（第十七轮专用 PoC 确证：播种 3 账号 → 损坏 → 注册 → 只剩 1 个）。

**它漏的不是我没看过的角落，是我自己确证过、打过补丁的缺陷。**

根因是那句老话：日志只保证"你知道自己丢了什么"，不保证"你没丢"。

建议三件事（W115/W127 已实现，供参考）：
- 每条被消除的命中登记样本，N 轮内抽样核验（本期 10% 起步）
- 核验必须**另起独立判据**——W109 对自身结论永远自洽
- 误杀修好可转绿，但**必须带判据编号**，只写"已修"不算

### ③ 核验脚本要负向测试，且用例本身也要验

W130 核验 div-zero 时我连错两版：

| 版本 | 漏什么 | 后果 |
|---|---|---|
| 正则版 | 只认 `if not X` / `max(1,..)` | 漏 `if stranger_signals:` 真值早退 ⇒ 误判 23 条无保护 |
| AST 版 | 只认 `If` 包裹 | 漏三元 `round(sum(sp)/len(sp),1) if sp else None` ⇒ 误判 21 条无保护 |
| v3 | 三形态全认 | **25 条全部有保护，0 条真缺陷** |

**如果我在第二版就停，会凭空造出 21 条缺陷。**

更关键的一点：**核验脚本的漏判没有任何东西会抓它——它就是判据本身。** 被测代码的漏判会被 PoC 抓到（M6 就是这样被专用适配器抓出来的），核验脚本没有上一层。

另外，负向测试的**用例本身也可能是错的**（W105 第一版把 `subprocess.run` 写成参数节点，构造出的用例无法触发判据）。

### ④ 工作流自身配置要能读回验证

两个真实事故：
- `focus.json` 用了 Python 式字符串隐式拼接，**JSON 不支持**——我建完没验证就能解析
- `coverage.json` 被我写坏过，条目 `id`/`title` 全丢，**没人发现**

共同点：**写配置时没遵守"写完要验证它真的生效"这条我自己定的纪律。**

建议：工作流配置在门禁里做 schema 校验 + 读回断言。

### ⑤ 定向专题 >> 泛扫（有数据支撑）

memory-agent 二十轮，**产出 high 的轮次全部是定向专题或覆盖盲区轮，没有一次是泛扫**：

| 轮次 | 模式 | 产出 |
|---|---|---|
| 01 | 定向：数据库 | **M1/M2/M5（high ×3）** |
| 02–13 | 泛扫 + 降噪 | 最高 medium，且有 4 轮 0 产出 |
| 14 | 定向 FOCUS-1 写入热路径 | M17（medium） |
| 15 | 定向 FOCUS-2 MCP/ACP | **M18/M19（high ×2）** |
| 16 | 定向 FOCUS-3 LLM 链 | M20（medium） |
| 17 | 覆盖盲区 COV-02 | 打通状态 PoC |
| **19** | **覆盖盲区 COV-07/08** | **M22/M23（high ×2）** |

建议：默认 `mode: focused`，每个专题配"四问"（能不能构造 / 崩溃后残留 / 资源耗尽 / 并发下是否正确），专题内**不做泛扫降噪**——降噪降级为专题结束后的副业。

### ⑥ 未覆盖面要显式 FAIL

"没扫到"和"扫过没问题"在报表里长得一模一样。覆盖面清单（W114）把前者挑出来显式告警，本期它一直挂着三条：

```
COV-01 依赖 CVE 面 已漏 18 轮        ← 网络 403，风险未知
COV-03 M3 部署路径确认 已漏 18 轮    ← 等用户答复
COV-08 补丁自洽性历史欠账 已漏 19 轮 ← 本轮处理，立刻出 M23
```

**COV-08 挂着 19 轮没人管，一管就出 high。** 这就是这条门禁的价值证明。

## 六、给维护者的优先级

1. **① 补丁自洽性**——成本最低、收益最直接（M23 是铁证，且名单按项目写死这个坑换项目必踩）
2. **② 降噪核验回路**——防止"降噪"变成"降低发现率"
3. **⑤ 定向专题优先**——有完整数据支撑，直接决定产出率
4. ③④⑥ 是纪律性建设，长期收益

## 七、如实说明

- 本提案基于**本地二十轮演进副本**，非官方 CLI 环境；`patch_lint` / `noise_ledger` / `run_final_audit` 都是我自己在副本里建的工具，与上游实现无关，仅作为"可工作的参考实现"提供。
- **依赖 CVE 面二十轮一次没扫**（pypi.org / osv.dev 均 403）——风险未知，不是无风险。
- 配套的规则提案 `py.guard_call_swallowed` 目前 **status=proposed，真实语料精确率 0/6**，它的价值是标定 gap-6（上下文判据），不是可启用规则。
