## 一、新增：2 条回归护栏规则

两条都源于规则**结构上看不见**的缺陷类，且 memory-agent 已在审计当日修复，故 intent=regression（0 命中=修复生效）。

### 1.1 `py.import_time_env_int`（medium，regression）

- **缺陷类**：模块导入期裸 `int(os.getenv(...))`。执行时机从「被调用」提前到「被 import」，两个后果：坏配置 → import 期 ValueError → 进程起不来（常驻容器即启动失败循环）；0/负值 → 护栏静默失效。
- **实证**：memory-agent 6 处（`store.py:52/55`、`rule_lifecycle.py:72/74`、`mcp_server.py:289`）。当日修复：新增 `env_cfg.py`（`env_int(name, default, lo, hi)`，畸形/越界回落默认不崩进程）并全部改接——**该规则当前在 MA 上 0 命中，即修复生效的直接证据**。
- **判据**：模块级 Assign/AnnAssign，value 是 `int()/float()` 调用且内含 `os.getenv/os.environ.get`；顶层 `try` 内的赋值视为「有降级」不报。
- **可移植性**：NAS 上 autoflow / deepseek2api / doubao2api 全是 getenv 配样式，零成本复用。

### 1.2 `py.health_gather_no_timeout`（medium，regression）

- **缺陷类**：health/ready 类函数用 `asyncio.gather` 汇聚子系统探测却不设 `asyncio.wait_for` 总超时——单个调用各有超时，但 **health 耗时 = 最慢子系统**；探针阈值远小于子系统超时之和，链条在接缝处断裂（慢查询 → health 挂 → 探针误杀 → 容器 churn）。
- **实证**：`runtime.py:health()` gather×1 无 wait_for（当日已修）；本轮另在 `vision_service.py:1344` 抓到一处**同类遗漏**——回归护栏与新发现两用。
- **判据**（三重收窄保精度）：函数名含 health/ready/status/ping/probe + 函数体内有 `asyncio.gather(` + 同函数无 `asyncio.wait_for(`；遍历用不下钻嵌套 def 的 `_iter_own`。

## 二、收敛：3 条既有规则（全部有 round-003→005 同目标对比数据）

| 规则 | 变更 | 前→后 | 依据 |
|---|---|---|---|
| `py.sql_limit_placeholder` | **YAML 正则 → Python 插件 v2.0.0** | 53 → **12** | v1 只认「LIMIT ?」形状，无法判绑定是否钳制；MA 实测 **32/32 全假阳性**（100% 噪音率）。v2 函数级判据：绑定裸形参且未经 clamp_limit/max/min 包裹才报；`int(limit)` 是 cast 不是 clamp，仍报 |
| `py.unbounded_container` | 加「赋值重置」识别 v1.0.2 | 8 → **6** | `self.X = []` 在业务方法里是周期重置（identity.py:428 每轮 reconcile 重置），旧判据只认 reset/clear 调用 |
| `GEN-02-sql-concat` | 负向预查 + 内部片段白名单 v1.1.0 | 8 → **4** | 行首 `(?!.*\?)`（同行有占位符=参数化）+ `" and ".join` 等常量分隔符 join 白名单（拼的是内部条件片段） |

### 收敛过程踩到的三个坑（已写进代码注释，供后人）

1. **`^(?!.*\?)(select...)` 把 select 锚到行首**——样本有缩进且 SQL 在字符串里 → dirty 0 命中、规则被标 broken。修法：`^(?!.*\?).*(select...)`。
2. **`\{\}` 撞 `str.format` 占位符语法**——format 只认 `{{`/`}}` 转义，`\{\}` 被当作字段名 `\` 抛 `KeyError: '\\'`。修法：改用 `str.replace("{name}", ...)`。
3. **`self.X = []` 的形状在 `__init__` 与业务方法里完全相同、语义相反**（初始化 vs 周期重置）——正则版把 dirty 样本的初始化当重置误杀。修法：AST 按所在函数判定，`__init__/__new__/__post_init__` 排除。

## 三、方法论四条（本次最重要的沉淀）

1. **「导入期副作用」应立为独立缺陷类别**。它与 PITFALLS 的静默失效族相反——**响亮失效**（直接崩），但同样致命；且现有全部判据都假设「缺陷在函数体里」。规则从不看导入期，于是这类缺陷 100% 在射程外。
2. **「已验证已修清单」应成为轮次报告必填小节**。本轮 §5 列了 10 项带 file:line 的已修项（WAL/RLock/transaction/checkpoint 超时跳过/分批 DELETE/MA40b…），直接避免下个 agent 重新审已修的东西——这是对「同一族第 N 次」现象的正面解法，与 family-level R1（族级清点）互补。
3. **「存活判据链」建议开为跨项目专题**：health/ready 是否有总超时 → 其依赖子系统各自超时多少 → 探针阈值是否匹配。D3 是完整实例；开发规范 §0 记载的 21 次容器崩溃全在这条链上。
4. **引用历史缺陷结论前必须重新实测**。本轮假设「chroma 无超时」被容器实测部分证伪（0.5.23 默认 query 60s）——历史记忆早于当前依赖版本。与 guardrail-wiring R5「引用历史命中数前确认工具代数」同族，但面向「历史结论」而非「历史数据」。
