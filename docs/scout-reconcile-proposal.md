# 建议书：审计工作流缺少「手猎 + 对账」阶段

> 提交对象：ADM-auditkit 维护者
> 来源：2026-10-11 关于「审计第一轮是否应轻装上阵亲自找一轮 bug」的讨论 + ADM-auditkit 自审（记忆 #54/#55/#56）实证
> 结论一句话：**审计工作流是经验的消费者，不是生产者。新项目首轮应插入「手猎 + 对账」阶段，其产出不是报告，而是下一轮规则的输入。**

---

## 一、原始命题与精确化

维护者提出：

> 审计第一轮应该让 agent 轻装上阵，亲自去找一轮 bug，这样才有可能有效沉淀出审计经验。直接用审计工作流那经验沉淀就很少了。对吗？

**判定：方向正确，但三个措辞需要精确化，否则落地会走偏。**

| 原始表述 | 精确化后 | 原因 |
|---|---|---|
| 第一轮「轻装上阵」 | 第一轮 = **手动优先 + 强制对账** | 价值不在「手动跑一遍」，而在「手动与工具的落差」 |
| 让 agent「亲自找一轮 bug」 | 产出 = **标定基线 + 项目方言表 + 规则原料 + 纠正画像** | bug 只是副产品，真正稀缺的是坐标系 |
| 直接用工作流「沉淀很少」 | 工作流是**经验消费者**；它产 A 类经验快、B 类经验慢 | 见下节两类经验框架 |

---

## 二、核心论断：工作流消费经验，不生产经验

审计工作流的本质是：

```
已有经验 --(编码)--> 规则/分析器 --(规模化执行)--> 命中 --(分诊)--> 报告
```

它把「人已经知道要防什么」编码成规则后批量跑。但**「这条规则为什么长这样」「这个新项目该防什么」这类原始经验，工作流本身产不出来**。只用工作流，就是在吃存量；存量吃完，产出归零。

### 两类经验的区分（关键）

| | **A 类：工具经验**（关于审计设施） | **B 类：领域经验**（关于被测系统） |
|---|---|---|
| 典型 | 别名表缺 `_atomic_write_text` → DO 规则静默 0 命中；BOM 致 `ast.parse` 抛错被吞；判据只看调用点名字，不看接收者语义 | 并发写盘丢数据；状态机在异常路径挂起；缓存键不含模型版本 → 换模型读旧结果 |
| 从哪来 | **工具失败时**，人去追查 | **主动推理代码**时形成假设 |
| 产物 | `PITFALLS.md` / `criterion-locality-proposal.md` / `rule-portability-proposal.md` | 那 16 项确证缺陷 / FOCUS 专题「四问」 |
| 工作流产出的速度 | **快**（工具一失败就暴露） | **慢**（看工具输出是被动反应，不是主动假设） |

### 实证（本仓库 docs 内自证）

- `docs/workflow-iteration-proposal.md` 列出 **11 次工具/环境静默失效**，无一例外表现为「结论变好」而非报错 —— 典型的 **A 类经验**：只有工具出错并被追查时才沉淀。
- `docs/criterion-locality-proposal.md` 自述：「第二期 20 轮里，**连续 6 轮的实质产出都是判据修正而非新缺陷**」—— 那 6 轮里 **B 类经验几乎为零**，工作流只在修自己。

**这就是「经验沉淀少」的真正机制**：不是工作流不好，而是它的产出结构天然偏向 A 类。B 类必须手动产。

---

## 三、为什么偏偏是「第一轮」：四个不可替代的作用

1. **标定基线（calibration）**
   没有手动基线，「工具 0 命中」**无法解读** —— 是干净？是不适用？还是规则坏了？
   这正是本仓库反复咬的那口：`unavailable ≠ safe`（`workflow-iteration-proposal.md` 建议二：`unavailable`（测不到）与 `safe`（没问题）必须严格分开，两者在报表里长得一模一样）。手动轮提供参照系。

2. **发现项目方言（vocabulary）**
   `rule-portability-proposal.md` 的铁证：DO 规则假设 AutoForge 的 `atomic_write_text`，而 doubao-butler 用 `write_json_atomic`，匹配不上 ⇒ 规则安静地 0 命中，而真缺陷存在。
   **手动读代码就能发现方言**，方言恰恰该沉淀进 adapter / rules。工作流不会替你发现方言。

3. **产生规则原料**
   工作流**运行**规则，不**写**规则。新规则的原料只能从手动推理中来。

4. **纠正画像**
   `config/projects.yaml` 里 doubao-butler 明确标注「技术栈未知，未探测前不得假定为 Python 项目」—— 工具画像可能错，手动读一眼就纠正了。

**一句话：第一轮手动，是为后面所有自动化轮建立坐标系。少了它，后面的自动化都在没有刻度的尺子上跑。**

---

## 四、关键修正：价值在「对账」，不在「手动」

这是最容易落地走偏的地方。

**如果第一轮只手动、后面只自动、中间不对账，你得到的是两堆互不相干的东西。** 真正产经验的是**那道落差**：

```
手动找到 3 个 / 工具报 0 个   → 工具漏了，为什么？   ← 最强信号（可能是规则失效）
工具找到 5 个 / 手动漏了 5 个 → 我的盲区在哪？       ← 次强信号（人的注意力盲区）
两者都没找到                  → 真盲区             ← 需人工确认
```

这与 `workflow-iteration-proposal.md` 里「失败开放 PoC」的教训同构：**只验「守卫放不放行」不够，必须追问「放行之后操作是否真的发生了」** —— 单侧验证都不算数，**必须双侧对账**。

## 五、建议形态

在 auditkit 现有 CLI（`profile / sync / list / selftest / round / status / pack / rules / propose`，均为单项目）中新增两个子命令：

```
auditkit scout <project>
    侦察 + 手猎轮。不跑规则引擎。
    强制产出四件套：
      ① 手猎假设清单（每条带「可证伪预测」：如果成立，应该观察到什么）
      ② 项目方言表（本项目用哪些 API / 惯用法 / 约定，供规则适配）
      ③ 候选规则草案（从手猎假设反推，落为 rules/ 或 adapter）
      ④ 该项目「四问」：能不能构造 / 崩溃后残留 / 资源耗尽 / 并发下是否正确

auditkit round <project> --round 2
    此时才上工作流（现有 round 不变）。

auditkit reconcile <project>
    强制对账：手猎结论 vs 工具结论，逐条落差异。
    ← 现在完全没有的一步，是经验沉淀的容器。
    输出不是报告，而是下一轮规则 / 适配器的输入。
```

### 产出物去向

| scout 产出 | 去向 |
|---|---|
| 手猎假设清单 | `projects/<name>/round-001/scout/hypotheses.json` |
| 项目方言表 | `projects/<name>/adapter/vocabulary.yaml`（供规则读取） |
| 候选规则草案 | `rules/project/<name>/` 或通用规则提案 |
| 四问 | 该项目的 `focus` / 专题规划 |
| reconcile 差异表 | 下一轮 round 的输入 + `PITFALLS.md` 增补 |

## 六、与「把实测提升为一等公民」的关系

本建议与 `workflow-iteration-proposal.md`（把 PoC 做成流水线一等阶段）**互补不冲突**：

- 那份提案管**自动化侧**：静态命中 → 行为级实测（PoC）。
- 本建议管**人的侧**：自动化之前，先由人建立坐标系，再由 reconcile 把两侧对齐。

两者共同的哲学是同一句：**静态给候选，实测/对账给确定性。**

---

## 七、边界（避免矫枉过正）

**手动优先 ≠ 手动万能。** 两个反例：

1. **规模化场景必须靠工具**：AutoForge 1237 条命中 → 收敛为 16 项确证缺陷，这个收敛手动做不完。手动轮只在「新项目首轮」和「工具结果可疑时（0 命中 / 命中骤降）」触发。
2. **A 类经验价值高于单个缺陷**：那 11 次静默失效的教训，让整台机器可信 —— 其价值高于任何单个 bug。所以不是「手动好、工作流差」，而是**两者产不同经验，缺一不可**。

## 八、落地路线（按成本递增）

| 阶段 | 动作 | 成本 |
|---|---|---|
| P0 | 在 `SKILL_USAGE.md` / `RULE_AUTHORING_GUIDE.md` 增加「新项目首轮先手猎」的流程规定（纯文档） | 极低 |
| P1 | 新增 `auditkit scout` 子命令骨架：建立 `scout/` 目录 + 四件套模板文件（不做自动分析，只强制结构） | 低 |
| P2 | 新增 `auditkit reconcile`：读取 scout 产出 + round findings，输出差异表（含「工具漏报 / 人漏报 / 共同盲区」三分类） | 中 |
| P3 | 把方言表接入规则层：规则声明 `assumptions`，adapter 提供方言（治本 `rule-portability-proposal.md`） | 高 |
